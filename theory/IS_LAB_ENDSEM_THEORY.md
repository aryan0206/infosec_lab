# IS Lab endsem theory: study from here

**Evidence key.** `Manual` means the supplied 68-page *IS Lab Manual_merged.pdf* explicitly covers the topic. `Question` means one of the four supplied previous endsem questions requires it. `Extra` is explanatory engineering context, not a course requirement. The manual says exam questions may combine or vary lab exercises (p. 7). It gives 20 marks to the endsem program (p. 3).

## 1. What the security operations mean

Confidentiality means an unauthorized reader cannot recover a message. Encryption addresses this, but the key must be protected too. Integrity means a change can be detected: `H(message)` changes when the bytes change. Authenticity means the claimed signer really controlled a private signing key. A digital signature combines a hash and a private-key operation; the verifier uses a public key. A bare hash does **not** authenticate its author. Non-repudiation also depends on reliable identity-to-key binding and key custody, not just a signature equation. These ideas recur in manual Labs 2, 5 and 6 and Questions B-D.

Choose exact bytes before hashing or signing. For JSON, use one canonical encoding such as sorted keys and compact separators. If either side hashes different whitespace or omits a field, verification fails or leaves that field unprotected. Sign the entire protected record, including ciphertext and meaningful metadata. Verify before any restricted decrypt action.

## 2. Labs 1-6 in one connected path

**Lab 1 (manual pp. 9-13): classical substitution and transposition.** Caesar/additive encryption shifts letters: `C=(P+k) mod 26`; with `A=0`, `C=(2+3)=5`, so C becomes F. Affine uses `C=(aP+b) mod 26` and needs `gcd(a,26)=1` for an inverse. Vigenere changes the shift with a keyword, and transposition changes positions rather than symbols. The examiner can ask for encrypt/decrypt, key validation, or known-plaintext attacks. A frequent error is dropping punctuation without saying so or choosing an affine multiplier with no inverse. These historical ciphers demonstrate mechanics; they do not protect modern records.

**Lab 2 (manual pp. 14-21): advanced symmetric encryption.** A symmetric cipher uses the same secret key for encryption and decryption. AES operates on 16-byte blocks and accepts 16, 24 or 32-byte keys (AES-128/192/256). CBC uses a fresh unpredictable 16-byte IV and padding: `C_i=E_K(P_i XOR C_(i-1))`, with the IV as `C_0`. CBC hides plaintext but does not authenticate it; add a MAC or signature if integrity is required. GCM uses a nonce and authentication tag; verification failure must stop decryption. Never reuse a GCM nonce with a key. A common mistake is calling a 24-character string “AES-192” without checking its UTF-8 *byte* length. Manual material also discusses block modes and DES; DES is historical and should be used only when explicitly assigned. `Extra`: prefer authenticated encryption for new designs. Question D explicitly requires CBC, so use CBC there.

**Lab 3 (manual pp. 22-31): asymmetric ciphers.** RSA chooses primes `p,q`, `N=pq`, `phi=(p-1)(q-1)`, public `e` coprime to `phi`, and private `d=e^-1 mod phi`. Textbook `c=m^e mod N`, `m=c^d mod N`. For actual confidential messages use a padded scheme such as OAEP; raw RSA is only an educational arithmetic exercise. ElGamal encryption publishes `(p,g,y=g^x mod p)` and keeps `x`; encrypt `m` with fresh `k` as `(g^k, m*y^k) mod p`, then divide out `(g^k)^x`. Rabin squares modulo `pq` and yields four roots on decryption, so encoding/disambiguation is necessary. Do not confuse ElGamal **encryption** with ElGamal **signature**.

**Lab 4 (manual pp. 32-43): key management and access control.** Diffie-Hellman exchanges `A=g^a mod p` and `B=g^b mod p`; both get `g^(ab) mod p`. For `p=23,g=5,a=6,b=15`, both derive `2`. Plain DH alone does not authenticate peers. Hybrid encryption uses a fresh AES session key for a record and wraps that key with the receiver's RSA public key; only the receiver's private key unwraps it. RBAC maps roles to actions. Key rotation and revocation must be represented in state; a menu label alone is not authorization. The manual describes larger enterprise key services, not a complete secure deployment recipe.

**Lab 5 (manual pp. 46-48): hashing and networking.** SHA-256 gives 256-bit digests and SHA-512 gives 512-bit digests. Python: `hashlib.sha256(data).hexdigest()`. Hash the exact bytes sent/stored. The lab also asks for a 32-bit educational hash starting at 5381, and socket-based hash comparison. A client comparing a server-supplied hash with its own hash detects accidental change only if the expected hash comes through a trusted/authenticated path. MD5 is required by Question C and by a Lab 5 comparison exercise, but collision attacks make it unsuitable for modern collision-resistant integrity.

**Lab 6 (manual pp. 48-53): digital signatures.** A signer hashes the exact message and signs with a private key; a verifier checks with the public key. RSA signing is different from RSA encryption. PKCS#1 v1.5 or PSS signing in PyCryptodome takes a hash object; RSA-OAEP is an encryption padding scheme and cannot be used as a signature. ElGamal signature uses a private exponent `x`, fresh `k` coprime to `p-1`, `r=g^k mod p`, and `s=k^-1(H(m)-xr) mod (p-1)`. Verify `g^H(m) = y^r r^s mod p`. Reusing `k` can expose `x`. Question D asks for this signature on the ballot SHA-512 digest.

## 3. Lab 7: partial homomorphic encryption (manual pp. 54-60)

Ordinary encryption lets an authorized party recover a message. Homomorphic encryption adds a special ciphertext operation that corresponds to a *limited* plaintext operation. You can calculate a total while keeping each input encrypted. It does not mean arbitrary Python expressions work on ciphertext; partial schemes support a specified algebraic operation.

### Paillier: add encrypted integers

Choose primes `p,q`; `n=pq`, `n2=n*n`, `lambda=lcm(p-1,q-1)`, often `g=n+1`, and `mu=L(g^lambda mod n2)^-1 mod n` where `L(u)=(u-1)//n`. Encrypt `0 <= m < n` with a fresh random `r` coprime to `n`: `c=g^m * r^n mod n2`. Decrypt `m=L(c^lambda mod n2)*mu mod n`. The **public** key encrypts and combines; only the **private** key decrypts.

Multiplying ciphertexts adds plaintexts: `Enc(a)*Enc(b) mod n2 = Enc((a+b) mod n)`. With toy `p=3,q=5,n=15,g=16,lambda=4,mu=4`, choose `r=1`: `Enc(2)=31`, `Enc(3)=46`, and `31*46 mod 225=76=Enc(5)`. Real encryption must use fresh random invertible `r`, not 1. A sum is only exact as an ordinary integer if it stays below `n`; otherwise it wraps modulo `n`. Validate this bound before claiming a monetary or glucose total. Do not decrypt each amount during the aggregation path.

### Textbook RSA: multiply encrypted integers

For public `(N,e)`, `Enc(a)=a^e mod N`. Thus `Enc(a)*Enc(b) mod N = (ab)^e mod N`. With `p=5,q=11,N=55,e=3,d=27`, `a=2,b=3`: ciphertexts `8,27`; encrypted product `8*27 mod 55=51`; `51^27 mod 55=6`. The result is `ab mod N`, **not** an unrestricted product. Question A bounds *each* input in `1..N-1`; that alone does not ensure `ab<N`. Print and check both the modular expectation and whether the ordinary product fits. Validate `p,q,e,d` or supplied `N,e,d` appropriately. RSA-OAEP randomizes/pads messages, so the textbook ciphertext multiplication identity does not apply. Never substitute OAEP for this exercise.

### ElGamal: multiply encrypted group elements

For ciphertext pairs `(c1,c2)`, componentwise multiplication modulo `p` gives encryption of the product modulo `p`. This is in the manual's additional Lab 7 exercises. Each encryption still needs fresh randomness. It does not directly give a sum. Reusing randomness or choosing invalid group parameters can break the demonstration.

**Exam selection:** “sum/total encrypted values” → Paillier; “multiply encrypted values” → textbook RSA if specified, or ElGamal if specified. Record inputs, encrypt separately, pass only ciphertexts to a separate combine function, decrypt only final combined ciphertext, and compare with the mathematical expectation. `Enc(a)+Enc(b)` is not Paillier addition; `Enc(a)*Enc(b)` is. Check ranges and wraparound. Aggregation alone does not provide authentication, access control, or protection against malicious input: Questions B-D combine it with those controls.

## 4. Lab 8: searchable encryption (manual pp. 61-68)

If a database is a single AES ciphertext, a server cannot readily search it without decrypting everything. A plaintext index is easy to search but reveals keywords. Searchable encryption stores encrypted records plus an index that supports authorized lookup without returning the plaintext record during search. In an inverted index, a token maps to document IDs. For example, `diabetes -> [P01,P03]`. A query returns identifiers first; decryption is a separate authorized action.

The manual introduces searchable symmetric encryption (SSE) and public-key searchable encryption (PKSE). Its Lab 8 exercises ask for ten text documents, AES-encrypted documents, an inverted index, and a search function; a second exercise sketches Paillier for an encrypted index. `Extra`: a stable keyed HMAC of normalized keywords is a practical *course demonstration* of search tokens: `token=HMAC(index_key, normalized_word)`, index `token -> encrypted record IDs`. The server can compare tokens but does not see the literal keyword. That still leaks repeated queries, which record IDs match, and result counts; low-entropy keywords may be guessed if the token key leaks. This is **not** a full formally secure SSE protocol. Paillier is randomized, so encrypting the same keyword twice does not yield directly comparable ciphertexts; the manual's PKSE sketch needs additional protocol details to make equality search work. Do not claim raw Paillier equality comparison is working PKSE.

In Question B, diagnosis search may return patient ID and name only, followed by verification-gated record decryption. In C, Grant ID lookup should return metadata or an index hit without revealing the encrypted description/amount. In D, constituency and time-window tokens can locate encrypted ballots; a simple local index may expose constituency/time to the storage operator. If an exam asks for true searchable encryption, state that a simple indexed demo has these limits. Normalize consistently (`strip`, lowercase, predictable date format), rebuild indexes after edits, and never print protected fields in a search result.

## 5. Question-specific combinations and limits

**A:** textbook RSA encryption + ciphertext multiplication + final decrypt. User-provided exam parameters; do not hardcode them. **B:** AES record/file protection, SHA-256 by ID, RSA dataset signature, Paillier glucose sum, diagnosis index, verification-gated decrypt. The exam dataset is supplied on the day. **C:** AES-192 description, Paillier amount, explicitly required MD5 hash, RSA signature, persistent records and role menus. Define whether the hash covers plaintext or ciphertext; sign the chosen canonical representation and verify it before review/aggregation. **D:** SHA-512 ballot hash, AES-256-CBC ballot, RSA-4096 key wrapping, ElGamal signature, Paillier tally, time validation and searchable index. A local machine clock is not a trusted timestamp. Basic secret sharing of a decryption key is a simulation, not threshold Paillier. Summing numeric candidate IDs is not a vector of per-candidate vote counts; for actual counts one encrypted indicator per candidate is needed.

**Practice check:** For each requirement, write the exact input, output, key owner, menu option, and failure behavior. Then demonstrate a round trip and a tamper rejection. Treat the manual's GnuPG and Snort items (p. 68) as additional tool exercises, not as implemented by a Python cryptosystem.
